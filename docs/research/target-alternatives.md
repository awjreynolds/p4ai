# Public alternatives for constrained compilation

Research for [Compare public alternatives to P4 for constrained compilation](https://github.com/awjreynolds/p4ai/issues/4), checked 17 October 2026. This is a provisional shortlist for a reproducible public demonstration with authentic constraints, no required hardware, and the user’s corrected priority: an actively developing target with career relevance. Tofino is excluded by user instruction. This does not select the target or establish hiring demand. **No toolchain, benchmark, proof, or claimed improvement was executed in this investigation.** Statements labelled “proposal” or “assessment” are deductions from the cited capabilities, not measured results.

## Comparison

| Candidate and concrete target | Authentic feasibility oracle | Separate correctness oracle | Proposed intervention and serious baseline | Assessment for this effort |
| --- | --- | --- | --- | --- |
| RTL → Yosys/ABC → nextpnr → Lattice iCE40 HX1K | Actual device packing, placement, routing; tool timing model | EQY sequential/combinational equivalence under explicit reset/environment assumptions | Select bounded synthesis recipes or equivalent RTL rewrites; compare default flow, recipe enumeration, random search, multiple placement seeds | Strong physical constraints; mature example target is weaker evidence for a current hardware career |
| C → Clang BPF → pinned Linux verifier, XDP subset | Real kernel acceptance, stack/instruction/analysis limits | Packet-output tests plus bounded equivalence for supported transformations | Repair verifier-hostile representations or select optimization sequences; compare Clang, fixed rewrites, search and K2 where compatible | Strongest fast, network-adjacent alternative; resource is partly verification complexity rather than chip capacity |
| C → Arm GNU Toolchain → STM32F100RB | Linked image against 128 KiB flash / 8 KiB SRAM memory regions | Benchmark checks in QEMU; stronger proof only for restricted transformations | Function-level inlining/unrolling/size choices; compare `-Os`/`-Oz`, LTO and budgeted flag search | Clear inexpensive size experiment; weaker multidimensional allocation story |
| IREE/MLIR or Triton → AMD MI350X (`gfx950`) | Compiler constraints and compiled register/LDS requirements | Source/reference comparison; compiled execution needs hardware or a validated target model | Dispatch configuration/tiling; compare IREE SMT enumeration, default schedules and autotuning | Leading technical candidate under active-target priority; offline feasibility and measured speed must stay separate |

P4 is covered by the companion investigation; compare concrete target/toolchain pairs, not language names.

## Open FPGA compilation

**Facts.** The public nextpnr flow explicitly supports iCE40 and ECP5, and documents `yosys ... synth_ice40` followed by `nextpnr-ice40 --hx1k`. Its architecture includes real commercial devices rather than an invented resource budget. The public OSS CAD Suite bundles synthesis, nextpnr, IceStorm, EQY and several SAT/SMT engines. [nextpnr](https://github.com/YosysHQ/nextpnr), [OSS CAD Suite](https://github.com/YosysHQ/oss-cad-suite-build).

EQY is a Yosys-based hardware equivalence checker with SAT and SBY strategies. Its documented treatment of X propagation makes assumptions about initialization and undefined values part of the experiment contract. Placement and equivalence are independent gates. [EQY documentation](https://yosyshq.readthedocs.io/projects/eqy/en/latest/).

**Proposal.** Begin with small synchronous packet-processing blocks: classifiers, checksum datapaths and bounded FIFOs. Freeze interface, latency and reset behavior. The agent may choose a synthesis recipe or propose a local equivalent rewrite; EQY must establish the specified relation before the candidate enters physical evaluation. Let nextpnr remain the allocator. Resource-fit success on a named device is the primary result; timing closure is a result against the pinned tool model, not a silicon frequency guarantee.

Start corpus discovery with [nextpnr-bench](https://github.com/YosysHQ/nextpnr-bench), which publishes iCE40 benchmarks, supplemented with independently licensed small packet blocks. Existing benchmarks may already fit easily: screen for authentic difficult cases and report that selection process. Do not quietly shrink the device model to manufacture failures. Audit individual designs before redistribution; a public repository is not itself a blanket redistribution license.

**Baseline and burden.** Compare the stock flow with a fixed portfolio of synthesis/ABC recipes and equal-budget random or enumerated recipe search, using multiple nextpnr seeds. SAT/SMT belongs in equivalence checking; a small exact resource-allocation model can be an additional lower-bound/control experiment, but cannot replace physical routing. Yosys and nextpnr publish ISC licenses; distribution dependencies and benchmark sources still need their own notices. [Yosys license](https://github.com/YosysHQ/yosys/blob/main/COPYING), [nextpnr license](https://github.com/YosysHQ/nextpnr/blob/main/COPYING).

**Assessment.** Strong for spatial allocation, but the maturity of iCE40 is a disadvantage under the corrected career priority. Current nextpnr also supports Nexus/Gowin; that establishes tool support, not a leading-edge silicon or hiring case. Proof/place-and-route cost needs measurement.

## eBPF

**Facts.** Linux checks register/pointer safety and program control flow, with internal analysis limits as well as instruction limits. Kernel documentation distinguishes the unprivileged 4,096-instruction limit from a one-million explored-instruction analysis limit; these are not interchangeable measurements. Pin the kernel commit/configuration, privilege mode and program type, and extract its actual limits rather than advertising one universal “eBPF budget.” [Verifier](https://kernel.org/doc/html/latest/bpf/verifier.html), [BPF design Q&A](https://kernel.org/doc/html/latest/bpf/bpf_design_QA.html).

The kernel supplies BPF selftests and a VM runner. This permits authentic kernel checks without NIC hardware, although it needs a Linux VM and suitable guest privileges rather than merely compiling on macOS. Selftests include expected failures and verifier regression cases: they are a useful oracle corpus, not automatically a representative optimization workload. [BPF selftest instructions](https://linux.googlesource.com/linux/kernel/git/bpf/bpf-next/+/8496d9020ff37a33c2a7b2fc84350fd03ffbde78/tools/testing/selftests/bpf/README.rst).

K2 is a particularly relevant mechanical comparator: stochastic synthesis with formal equivalence checking and public packet-processing benchmarks. Its artifact separates optimization, kernel acceptance and network throughput experiments; some optimized outputs did not pass the kernel checker. Thus a model's confidence, K2's proof, and kernel acceptance cannot substitute for one another. The source is MIT licensed, but its installation pins an old Z3 and documents older environments, so present-day reproducibility remains untested. [K2 artifact](https://github.com/smartnic/sigcomm21_artifact), [K2 source](https://github.com/smartnic/superopt).

**Proposal.** Use a narrow XDP subset with immutable map layout and bounded packet reads. Escalation chooses among checked rewrites addressing stack use, duplicated branches or verifier state growth; it cannot remove safety checks or change the specification. Keep packet outcomes and state updates as a separate correctness contract. Limit K2 proofs to supported instructions/helpers; unsupported proofs remain unresolved.

Compare Clang optimization levels, fixed rewrite rules, budgeted search, and K2 on their common supported subset. Include K2's published kernel/Cilium-derived examples and curated kernel tests with provenance. A newer primary paper, EPSO, reports cached superoptimization improvements over K2; its executable availability and current-kernel coverage were not established here, so it is a baseline-discovery item, not an assumed runnable dependency. [EPSO paper](https://arxiv.org/abs/2511.15589).

**Assessment.** eBPF preserves the user's networking advantage and gives a crisp public accept/reject loop. It is the leading alternative for demonstrating escalation economics quickly. It demonstrates constrained compilation into a verified execution environment; it does not reproduce Tofino's placement problem.

## Constrained MCU compilation

**Facts.** STM32F100RB provides a concrete Cortex-M3 target with 128 KiB flash and 8 KiB SRAM. QEMU documents `stm32vldiscovery` and its emulated/unsupported peripherals. GNU ld memory regions make the linked image fail when allocated sections exceed their declared region. [ST target](https://www.st.com/en/microcontrollers-microprocessors/stm32f100rb.html), [QEMU board](https://www.qemu.org/docs/master/system/arm/stm32.html), [GNU ld MEMORY](https://sourceware.org/binutils/docs/ld/MEMORY.html).

**Proposal.** Restrict the first task to flash fit, with statically allocated RAM and an explicit stack reservation. A link map does not bound peak stack, heap, interrupts or timing. Use Arm GNU Toolchain, a pinned linker script and QEMU functional checks; exclude unsupported peripherals and dynamic allocation. Candidate choices could alter per-function inlining, unrolling or constant-table representation while preserving behavior.

Embench offers public embedded workloads and built-in benchmark validation, designed for real or simulated execution. Its performance scores require cycle-accurate simulation; exclude ordinary emulator timing. The repository is GPLv3 with some individually dual-licensed benchmarks, so fetch pinned upstream sources and preserve their licenses separately from this MIT harness. [Embench](https://github.com/embench/embench-iot).

The baseline should include size-oriented GCC optimization, LTO, dead-section elimination and a budgeted flag/parameter search before invoking an LLM. GCC documents the optimization controls. Count the whole load image with identical libraries/startup code. [GCC options](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html), [Embench size methodology](https://github.com/embench/embench-iot/blob/master/doc/README.md).

**Assessment.** This offers the simplest credible resource count, but near-limit real applications and a nontrivial transformation space need discovery. It risks becoming ordinary compiler-flag tuning with little need for high-level reasoning.

## Current accelerator/kernel compilation

**Facts.** IREE is an MLIR-based compiler/runtime; its ROCm deployment documentation names MI350X/MI355X (`gfx950`, CDNA4), distributes the ROCm compiler in `iree-base-compiler`, and supports an explicit target argument. AMD also lists MI350 in its current compatibility matrix. This supports a concrete current target rather than a generic “GPU” proposal. [IREE ROCm deployment](https://iree.dev/guides/deployment-configurations/gpu-rocm/), [AMD compatibility](https://rocm.docs.amd.com/en/docs-7.2.3/compatibility/compatibility-matrix.html).

IREE exposes compiler-generated constraints covering shapes, workgroups, subgroups, MMA choices and shared memory. Its tuner serializes constraints to SMT-LIB, enumerates valid assignments and asks the compiler to materialize tuning configurations. The constraint verifier is explicitly experimental. This is unusually close to the proposed mechanical-first architecture; it also creates a strong baseline an LLM must beat. [IREE tuning](https://iree.dev/reference/tuning/).

**Proposal.** Start with fixed-shape matmul/reduction dispatches and a pinned `gfx950` lowering pipeline. Escalation ranks legal configurations or selects bounded decomposition alternatives after deterministic/compiler/solver screening. Do not ask the model to rediscover arithmetic resource limits. Compiler success, constraint satisfaction and final binary resource reports form separate offline gates; they do not prove runtime numerical correctness. Restrict accepted transformations to trusted compiler schedules initially, preserve math-mode assumptions and report target execution as pending when unavailable.

LLVM documents AMDGPU resource metadata and occupancy calculation. Occupancy is a prediction, not throughput; register spilling is not necessarily a hard compilation failure. Triton’s interpreter bypasses compilation, so it cannot certify generated GPU code. [AMDGPU backend](https://llvm.org/docs/AMDGPUUsage.html), [occupancy calculator](https://www.llvm.org/docs/CommandGuide/llvm-calc-occupancy.html), [Triton interpreter](https://triton-lang.org/main/programming-guide/chapter-3/debugging.html).

Compare IREE defaults plus SMT enumeration/ranking; for a Triton variant include its autotuner, and consider TVM DLight/MetaSchedule for a common workload comparison. These alternatives already search schedules: the claim should concern quality per total search cost. Public starting corpora include compiler-extracted IREE dispatches and [Meta/PyTorch TritonBench](https://github.com/meta-pytorch/tritonbench/blob/main/README.md) (BSD-3-Clause, with separately licensed dependencies). [Triton autotuning](https://triton-lang.org/main/python-api/generated/triton.autotune.html), [TVM search](https://tvm.apache.org/docs/deep_dive/tensor_ir/tutorials/meta_schedule.html).

**Assessment.** Promote IREE/MLIR AMDGPU to the leading technical shortlist under the corrected priority; Triton is a strong alternative interface. Compiler-only development is public and can be hardware-independent, subject to a build smoke test. Numerical/performance benchmarking needs rented, borrowed or owned compatible GPUs and pinned runtime/driver versions; prices and access were not investigated. MLIR, LLVM lowering, constraint modelling and kernel scheduling are transferable skills by technical inference, not evidence of a job offer. IREE publishes Apache-2.0 with LLVM exceptions; dependency and workload licenses remain separate. [IREE repository](https://github.com/iree-org/iree).

## Provisional shortlist and fair experiment

Shortlist **IREE/MLIR targeting current AMDGPU**, **eBPF**, and **P4 only with an actively developing concrete target that passes public-access checks**. Retain FPGA as a physical-allocation comparator; demote an iCE40-only demonstration and MCU flag tuning for the corrected career priority. This is a technical assessment, not the human choice or hiring research. The key unresolved tradeoff is whether an offline feasibility demonstration is sufficient or the first experiment also needs funded GPU validation.

For any choice, predeclare family-separated development/evaluation cases, success constraints, attempt limits and stopping rules. Compare mechanical-only, mechanical→JEV→high-reasoning, and high-reasoning-only policies. Charge failed candidates, proof timeouts, compiler invocations, CPU-seconds, peak memory, elapsed time and model spend; count shared preprocessing and amortize cached-rule discovery explicitly. Report feasible-and-correct coverage at equal budgets, not merely best output quality. Publish immutable tool/corpus/model identifiers, seeds, prompts, raw diagnostics and replayable decisions. These are proposed experimental controls; none has yet been validated by a run.
