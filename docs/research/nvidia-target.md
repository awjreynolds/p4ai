# NVIDIA GPU compiler target assessment

Research date: 17 October 2026. Primary-source assessment for [Assess a current NVIDIA GPU compiler target](https://github.com/awjreynolds/p4ai/issues/9). No toolchain was installed, built, or executed; reproducibility below is supported by documentation and code inspection, pending a bounded build spike.

## Provisional route

**Triton's NVIDIA backend targeting Blackwell B200 (SM100) is the strongest first candidate for an inspectable compiler intervention.** Start with shared-memory allocation for fixed lowered IR, with mechanical solvers before any learned escalation. This is an authentic bounded resource problem and produces compiler-engineering evidence; whether escalation adds value remains an experimental question. B200 is explicitly supported in NVIDIA's architecture matrix, whereas consumer Blackwell SM120 is a different target. Architecture-accelerated `sm_100a` features require matching hardware; do not advertise the artifact as portable across Blackwell GPUs. [NVIDIA architecture matrix](https://docs.nvidia.com/cutlass/latest/overview.html)

## Authentic constraints and reproducibility

B200's compute capability 10.0 has 228 KiB shared memory per SM, at most 227 KiB per block, 64K 32-bit registers per SM, up to 255 registers per thread, and 64 resident warps per SM. Shared-memory allocations above 48 KiB require dynamic allocation and explicit opt-in; CUDA reserves 1 KiB per block. These are real architecture restrictions, not a synthetic memory budget. Begin with one CTA, fixed arithmetic precision and no cluster policy changes. [Blackwell tuning guide](https://docs.nvidia.com/cuda/blackwell-tuning-guide/index.html)

Triton's `compile` function accepts an explicit `GPUTarget("cuda", 100, 32)`, avoiding default device discovery. Its compilation pipeline produces cubin before lazily initializing runtime handles. That supports a GPU-free Linux compilation harness using AST signatures or saved IR; ordinary tutorial scripts can still allocate GPU tensors during import and require adaptation. Pin compiler revision, LLVM dependencies, assembler version and every configuration. Public availability does not mean every tool is open source or covered by this repository's MIT license. [Compiler source](https://github.com/triton-lang/triton/blob/main/python/triton/compiler/compiler.py), [installation instructions](https://triton-lang.org/main/getting-started/installation.html)

Crucially, some resource rejection occurs during runtime-handle initialization against device properties. A successful compile therefore does not establish launchability. Record Triton's dynamic shared-memory metadata plus `cuobjdump --dump-resource-usage` register, static shared, stack and local-memory information. Implement a separately reviewed target check, including launch dimensions, allocation granularity, dynamic-shared opt-in and any Tensor Memory usage. Until covered, exclude affected kernel families. Register pressure can cause spills rather than compilation failure; resource reduction and calculated occupancy are not measured speedups. [Runtime checks](https://github.com/triton-lang/triton/blob/main/python/triton/compiler/compiler.py), [CUDA binary utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/)

## Narrow first experiment

**Proposed boundary:** intercept shared-memory allocation after buffer requirements and conflicts have been computed, before offsets are committed. Keep source, arithmetic, layouts and scheduling fixed. Triton's allocator currently sorts buffers by descending size, chooses initial placements, builds interference, and applies first-fit coloring with repeated offset adjustment. Its source explicitly identifies an example of wasted space. This is a concrete investigation point, not evidence of a useful benchmark improvement already achieved. [Allocation implementation](https://github.com/triton-lang/triton/blob/main/lib/Analysis/Allocation.cpp)

Extract an allocation instance containing sizes, alignments, aliases, liveness, asynchronous-region conflicts and partition restrictions. Candidate outputs are offsets or a finite allocation strategy. An independent checker must reject overlapping conflicting buffers, invalid alignment, broken aliases and invalid partition placement before compiler replay. A simplified interval-packing model that omits concurrent regions would be unsound. Proof is relative to the extracted constraints; it does not prove extraction or the complete backend correct.

Use unchanged upstream allocation as the first baseline, then deterministic ordering portfolios, randomized restarts, and an exact SMT/CP-SAT/ILP formulation on tractable instances. For larger instances give solver and heuristic portfolios the same wall-clock and compilation budgets as escalation. Simple `num_stages`/`num_warps` enumeration is also a strong control when comparing whole-kernel configurations: Triton already exposes these parameters and autotunes configurations. Do not claim an LLM contribution for discovering a setting an inexpensive finite search finds. [Configuration API](https://triton-lang.org/main/python-api/generated/triton.Config.html), [autotuning API](https://triton-lang.org/main/python-api/generated/triton.autotune.html)

The escalation experiment should ask whether mechanical → typesafe.ai → stronger-model selection saves total search cost on difficult instances. Learned tiers select strategies or search budgets; the checker decides legality. Report compile time, solver time, model cost, peak shared memory, spill changes, rejection rate and success under the published target limits. An informative outcome may be that exact or portfolio methods dominate and escalation is unnecessary.

## Corpus, correctness and decision gate

Start with public Triton attention, persistent-matmul and grouped-GEMM examples, plus allocation regression cases; freeze revisions and publish shape/configuration generation. Hold out kernel families rather than merely shapes. Seek naturally occurring cases where the upstream allocation exceeds B200's legitimate limit and a verified allocation fits. If none exist, report memory reduction or search-cost results and reject the proposed resource-repair claim. [Triton tutorials](https://triton-lang.org/main/getting-started/tutorials/)

CPU reference calculations and Triton's interpreter can check supported source-level behavior, but the interpreter bypasses GPU compilation and has documented limitations. They cannot validate changed binary addresses, synchronization or races. A later rented/partner B200 run should compare outputs, exercise boundary cases and run Compute Sanitizer before claiming executable correctness or performance. No owned GPU is necessary; **no GPU execution at all means a compiler/resource demonstration only**. [Triton debugging guidance](https://triton-lang.org/main/programming-guide/chapter-3/debugging.html)

Proposed resolution: retain Triton→B200 as the leading technical candidate, conditional on a GPU-free compile/resource extraction spike and a corpus showing genuine allocation headroom. Keep IREE CUDA as the alternative if broader MLIR model compilation better matches the desired role. Do not promise an LLM win or performance result before those gates pass.
